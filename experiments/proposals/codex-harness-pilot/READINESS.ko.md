# Codex 맞춤 하네스 효과 파일럿(48회) 준비물 — NOT_READY

**작성일:** 2026-10-05 · **상태:** 준비물 정리 / 구현·실행 없음 · **설계 원본:** 노션 「AutoHarness — GPT 구독자를 위한 프로젝트 맞춤 하네스 생성·검증」 6·7·15·16절

이 문서는 기존 설계의 48회 파일럿을 시작하기 위해 필요한 준비물과 현재 상태를 정리합니다. 설계를 새로 바꾸지 않으며, 아래 "제안"은 사용자 결정 전까지 확정이 아닙니다. 이 문서 작성 과정에서 모델 호출, GPU 실행, 유료 API 호출은 하지 않았습니다.

## 1. 파일럿이 답할 질문과 답하지 않는 질문

- **답할 질문:** 같은 GPT(Codex)가 자동 생성된 프로젝트 맞춤 하네스를 받으면 기준선보다 더 잘 구현하는가(H2), 범용 지침보다 나은가(H3). 지금까지의 실험(10/03 24회, 10/04 48회·216회, 10/05 192 cell)은 모두 **생성 모델의 출력 품질**만 봤고 이 질문에는 답하지 않았습니다.
- **답하지 않는 질문:** 짧고 모호한 요청의 자율 해결(인계 문서의 P0~P4). 이 파일럿은 명확한 요청으로 고정합니다. 결과를 모호한 요청 효과로 확대 해석하지 않습니다.

## 2. 고정 설계 요약

| 항목 | 값 |
|---|---|
| 프로젝트 | 합성 2개(추천: 이슈 트래커, 행사 신청 서비스), 같은 기술 스택, 프로젝트별 baseline 커밋 1개 |
| 과제 | 프로젝트당 FE·BE·통합 3개 = 6개 (IT-FE, IT-BE, IT-INT, EV-FE, EV-BE, EV-INT), 서로 독립 |
| 조건 | A 기준선 / B 범용 하네스 / C1 M1 생성 하네스 / C2 M2 생성 하네스 |
| 반복 | 조건·과제당 GPT 2회 → 6 × 4 × 2 = **48회 구현 실행** |
| 하네스 | M1·M2가 프로젝트별 1회 생성 = **4개**, 같은 프로젝트 3과제에 재사용, 재생성 금지 |
| 주 지표 | 무개입 과제 성공률(필수 요구사항 + 사전 지정 회귀 검사 전부 통과) |
| 제안 게이트 | 조건당 12회. C−A **+10%p 이상 = 순성공 2건 이상**, 새 심각 회귀·완료 오판 0건, C−B도 함께 보고. C1/C2는 합치지 않고 따로 보고 |

이 파일럿 전용 자산은 저장소에 **하나도 없습니다.** 재사용할 수 있는 것은 다음뿐입니다.

| 10/05 교훈 | `experiments/results/` | 생성 모델 출력은 JSON Schema 제약(J1)이 사실상 필수. F·R은 이득 없음 |

## 5. 작업 묶음별 준비물

각 항목의 완료 조건을 충족해야 G0/G1(10/09)을 통과합니다. 현재 상태는 전부 **없음**입니다.

### W1. 합성 프로젝트 baseline 2개

- [ ] 이슈 트래커 baseline: 목록·필터·정렬, 상태 변경 API, 사용자 조회·권한. 담당자 기능용 저장소 계약 명시
- [ ] 행사 신청 baseline: 신청 폼, 신청·취소 API, 정원, 순차 대기 등록 정상 동작, 대기 명단 UI/API/DB
- [ ] 각 baseline에 세 과제의 독립 결함·미완성 기능을 함께 심고 커밋 1개로 동결
- [ ] 기존 지침(`AGENTS.md`, README, 테스트 명령)을 실제 프로젝트처럼 포함. A 조건에서도 삭제하지 않음
- [ ] baseline failure manifest: 다른 과제의 의도된 결함과 무관한 기존 실패 기록
- [ ] family·계보 기록: 템플릿 작성자, 변형 이력, 정답 암시 주석·TODO 부재 점검
- [ ] 하네스 생성 **전에** 동결, 작성자 외 검토자 검수

### W2. 과제 6개와 채점 계약

- [ ] 과제별 사용자 요청 원문(명확한 요청)과 요구사항 YAML(노션 16.2 스키마)
- [ ] 노션 16.3에서 "새 제안"으로 표시된 규칙 확정: 상태 그래프와 응답 코드, 알 수 없는 필터값 정규화, 대기 순서 tie-break, 중복 클릭 정책 등
- [ ] 공개 검사 `tools/check_public.py --task TASK_ID` (프로젝트 저장소 안)
- [ ] 비공개 검사 `grade.py --task TASK_ID --submission DIR` (D4 저장소, 구현 작업 공간에 마운트하지 않음)
- [ ] fixture 초기화, 시계·timezone·seed 고정, 동시성은 barrier로 실제 중첩 실행
- [ ] timeout: 명령 120초, UI assertion 10초, 동시 배치 10초(제안). 기동 실패·timeout·assertion 실패 구분

- [ ] `render`: 고정 템플릿으로 `AGENTS.md` 관리 영역 + 영역별 `SKILL.md`. 존재하는 영역만 생성

- [ ] 로딩 판정은 모델 자기 보고가 아니라 실행 로그의 파일 읽기·주입 증거로
- [ ] B와 C의 지침 토큰 상한을 같게 하고 실제 길이 기록

### W5. 구현 실행기

- [ ] 실행마다 baseline 커밋에서 새 작업 사본과 새 세션, 이전 과제 결과 비전달

- [ ] 실행 종료 후 작업 공간 밖에서 비공개 채점, 실행별 manifest 작성
- [ ] 지표: 무개입 성공률, 요구사항 충족률, 첫 구현 통과율, 회귀, 완료 오판, 개입, 시간, 사용량, 하네스 유효률
- [ ] 보고: 조건별 12회 분모, 프로젝트별 6회·과제별 2회 원자료, C1/C2 분리, 48회를 독립 표본으로 취급하지 않음
- [ ] 미실행·인프라 실패를 성공이나 0으로 채우지 않음

### W7. G0/G1 리허설

- [ ] 1과제 × A·C 조건으로 생성→적용→Codex 구현→공개·비공개 채점까지 1회 연결 (파일럿 집계에서 제외)

- [ ] 끝나지 않으면 **실행 전에** 범위 조정을 결정하고 기록. 결과를 본 뒤 과제를 빼지 않음

## 7. 알려진 위험

- **구독 자동화:** Codex의 비대화형 실행·사용량 한도가 계정에 따라 다를 수 있습니다. 확인 전에는 처리량을 추정하지 않습니다.
- **합성 환경 편향:** 같은 작성자가 프로젝트·과제·채점기를 만들면 하네스에 유리하게 설계될 수 있습니다. 결과는 해당 합성 환경의 효과로 한정합니다.
- **누출:** 과제 정보가 baseline 주석·커밋 이력·생성기 입력으로 새면 C 조건이 부당하게 유리해집니다. W1·W3의 누출 점검이 필수입니다.
- **소표본:** 조건당 12회이므로 결과는 개선 신호이지 통계적 입증이 아닙니다.
- **목표 불일치:** 이 파일럿이 성공해도 인계 문서의 핵심인 짧은 요청 자율 해결은 검증되지 않습니다.
